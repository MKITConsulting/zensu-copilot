# Phase 6 step 10.5: consume, fix rounds and terminal routing

Read this entire reference after [review-verification.md](review-verification.md), before issuing a review ticket, and again whenever the post-review hook routes this round. A routed fix round returns to the ordered references in [review-chain.md](review-chain.md).

## Consume task prompt format

For `agent_type: zensu:code-reviewer`, use a unique task `name`, `description`, and `mode: "sync"`. Its `prompt` starts with the exact two header lines below, without an introduction or fences. Replace the example ticket with the newly issued ticket and the packet line with the exact helper output. The `REVIEW-PACKET:` reference must occupy its own line, without prose, indentation, a bullet, quotes, backticks or appended text. Follow it with this round's actual verified merged findings; `(no findings)` is valid only for an empty list.

```text
PRE-MERGED FINDINGS (fan-out)
REVIEW-TICKET: rt_actual_ticket
REVIEW-PACKET: /absolute/project/.zensu/reviews/run.example/round-1-packet.json sha256:<64-hex-digest>
merged_findings:
- (no findings)
```

For an Autopilot-bound chain, insert the three exact delegated-envelope lines specified in step 5 immediately after the ticket and before the standalone packet line. Preserve all binding values and the first two lines unchanged.

5. **Thin consume-mode spawn (the single hook trigger).** Immediately before every ticket/spawn, a bound chain MUST read fresh `--autopilot-status` and require the current session owner, `stage=TDD_RUNNING`, `tdd.sessionId`, `tdd.attempt`, `tdd.chainId`, and `tdd.returnStage` to match `RUN_ID`, `ATTEMPT`, `CHAIN_ID`, and `RETURN_STAGE`; stale or incomplete evidence blocks before the ticket is issued. First issue a one-shot ticket with `REVIEW_TICKET="$(COPILOT_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --review-ticket)"`; an empty value is a blocker and you MUST NOT spawn — when it persists, read the chain shape with `COPILOT_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --chain-status` and follow the supported command it names (`/zensu-recover-chain` owns the one shape no other command can leave); never arm a fresh chain to work around it, because that grants a new review budget. Then spawn ONE `zensu:code-reviewer` with the task tool (`agent_type='zensu:code-reviewer'`, `mode: "sync"`). Its prompt MUST start with exactly two header lines — first `PRE-MERGED FINDINGS (fan-out)`, second `REVIEW-TICKET: ${REVIEW_TICKET}`. A standalone chain follows those two lines with the exact `REVIEW-PACKET` reference and carries no delegated envelope. A bound chain appends these three official lines immediately after the ticket, each exactly once and unchanged: `ZENSU-DELEGATED-CALLER: autopilot`, `AUTOPILOT-BINDING: run=${RUN_ID} attempt=${ATTEMPT} chain=${CHAIN_ID}`, and `AUTOPILOT-STAGE: ${RETURN_STAGE}`; then append the exact `REVIEW-PACKET` reference. Preserve that envelope exactly once through the post-review handoff into `/zensu-self-review`. After the reference append the merged findings from step 4 (including the step-4b judge deltas and the step-4c `[Unverified — do not fix]` annotations). A partial, duplicate, malformed, or conflicting envelope is a fail-closed blocker; do not issue another ticket to work around it. The reviewer runs in consume mode under `reviewer-readonly-v1` — no shell, build, test, workflow mutation, or nested agent — and emits the consolidated report only from supplied evidence and findings. Its report rates finding severity; it MUST NOT invent a fix-round or convergence directive. The authoritative native post-review hook resolves `autoFixSeverity`, suggestions, neutralizations and round budget and supplies the sole next-action decision. An IMPORTANT finding may remain advisory for panel routing under critical-only policy while still requiring attention during terminal self-review; keep those distinct. The hook atomically consumes that ticket and advances `reviewRound` in the same revisioned Session Control workflow document, so duplicate or prior-chain Agent completions are no-ops. Issue a fresh ticket before EVERY verification spawn. Do NOT ask the user about review — running the review step IS the autonomous action, the full native fan-out.

- **`--chain-done` is the chain-terminus marker, now owned by the `/zensu-self-review` stage.** Run it yourself ONLY when (a) implementation produced ZERO file changes (every step blocked `[!]`) — then run it INSTEAD of spawning the reviewer and stop; or (b) `hooks.selfReview` is disabled and the reviewer returned PASS / suggestions-only; in case (b) first run step 6d's `--acceptance-status` and, when it exits non-zero, `/zensu-verify-feature --chain`, because review rounds change the tree the acceptance records are bound to. Standalone chains use the existing unqualified command — and that command verifies the claim: it refuses while `git diff --name-only HEAD` or an untracked non-ignored file still reports a changed file, so in case (b) the reviewed terminus MUST carry `--claimed-review-ticket`. In zero-change case (a), a bound chain MUST use `COPILOT_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --chain-done --autopilot-run "$RUN_ID" --autopilot-attempt "$ATTEMPT" --chain-id "$CHAIN_ID" --outcome no-changes`; never let the helper's normal `pass` default mislabel that receipt. In reviewed case (b), use the same bound command without an explicit outcome and append `--claimed-review-ticket "$REVIEW_TICKET"` whenever a ticket was issued. When self-review is enabled (the default), the reviewer convergence routes to `--code-review-done` + `/zensu-self-review`, carrying the exact binding evidence so that skill issues the same bound terminus. **NEVER** issue `--chain-done` in the same turn or batch as `--tdd-complete`, the reviewer spawn, a plan write, or the audit — landing it early releases the Stop gate before review and silently defeats the chain.

- The `post-review-tdd-delegate.sh` hook routes the reviewer's findings back to you. **Applies to EVERY routed round before it re-verifies, in every severity mode (including a suggestions-only round under `autoFixIncludeSuggestions`) — the terminal `/zensu-self-review` fix round is the ONE exception, being the chain's last edit, and runs the full suite through the evidence runner per that skill: if you changed a file, log this round's `R{N}-<step> IMPL completed — files:` claims (`{N}` is the fix round the post-review directive names), re-run the Phase 6 step 5b native file editing Landing Audit over them, and re-run this round's OWN scoped suites, logging a fresh CHECKPOINT line — the packet you are about to rebuild carries `test_evidence`, and a verdict measured before this round's edits describes a tree that no longer exists. The full suite returns in the convergence branch below, at a max-rounds hand-off and in that self-review fix round, never in a routed one.** — a fix round is exactly where a no-op replacement hides, and the round's own claims are never covered by the single Phase 6 pass. On re-runs the finding does not re-open the closed Phase 6 gate; it MUST instead be carried verbatim into the round status line and the CHAIN-END SUMMARY. On routed findings (only Critical ones under the default `hooks.autoFixSeverity: critical`): fix them in THIS thread under the same TDD discipline (re-enter Phase 4 cycles — the gate is still active), then re-run the persona helper, rebuild REVIEW PACKET v1 — and when `hooks.incrementalReviewRounds` is enabled (the default) keep the canonical packet unchanged and pass a separate aspect-only `review_scope` with this round's OWN delta: run `node "{plugin_root}/hooks/lib/review-round-scope-v1.js" --log {log_file} --round {N} --root "$TOP"` and use its `file` lines UNION every path a still-open finding cites, but ONLY on `status=ok`. `status=empty` and `status=degraded` both mean the delta could not be established, and there `review_scope` keeps the WHOLE diff — reviewing a file twice costs tokens, reviewing nothing costs the guarantee. The canonical packet ALWAYS keeps the full cumulative `changed_files`; `zensu:review-judge` ignores any aspect-only `review_scope`, because cross-cutting drift into a file THIS round did not touch is exactly what a delta hides, and that is the one finding class the narrowed panel structurally cannot raise. Then re-fan-out the aspects/personas, re-run the step-4b judge when `hooks.reviewJudge` is enabled, and re-run the step-4c Finding Verification Gate over THAT round's merged list when `hooks.findingVerification` is enabled, before the consume reviewer (never carry a prior round's packet, `JUDGE-*` deltas, or verification verdicts forward — a fresh round's findings cite fresh line numbers, so last round's anchors prove nothing about this one). When `hooks.reviewConvergence` is enabled (the default) the post-review directive adds a review-convergence clause: follow it to ledger every merged finding as a `FINDING LEDGER` run-log line, to resolve `hooks/lib/review-ledger-v1.js`, and to classify the re-review's merged list after the verification gate. The ledger is history for the judge only, never a finding list and never a verification verdict, so the rule above still holds. On PASS / suggestions-only (and on `autoFixMaxRounds` convergence): FIRST, run the Phase 6 step 1 full-suite command again with `--if-stale`: it skips when the newest full-suite record is green on the current tree and otherwise re-runs `{full_test_cmd}` over the current tree — this branch is the one decidable moment at which the chain knows it is converging, so it is where the closing verdict is measured; then run `--code-review-done`, then invoke the `/zensu-self-review` skill (read `{plugin_root}/skills/zensu-self-review/SKILL.md` with native view and execute it in this main thread with the stated input) — the terminal self-review stage. **The self-review stage owns `--chain-done`**: it re-reads this session's changes, takes at most one fix round (never re-running the reviewer), then runs `--chain-done` and renders the final CHAIN-END SUMMARY (with a `## Self-Review Summary` section). Do NOT run `--chain-done` or render the summary yourself when self-review is enabled (the default). The loop ends at PASS or `autoFixMaxRounds`, then self-review finalizes. After the chain closes, when the session plan carries a `## Requirements` table, offer `/zensu-converge` as an optional flow-back audit next step, using this exact line: `Optional next step: /zensu-converge — flow-back audit of the code against the plan's Requirements table.` (offer only — never run it unasked). Never render it for an Autopilot-bound chain in any `hooks.selfReview` setting — autopilot runs converge report-only at the autopilot skill's own step 2b and that run is non-interactive. When `hooks.selfReview` is enabled (the default), `/zensu-self-review` renders that offer in its `## Open` section under the standalone-only condition stated there — do not render it a second time here; when it is disabled, this thread is the only carrier and renders it itself. The offer travels only inside the combined-summary directive, so any branch emitting no combined summary suppresses it: with `hooks.selfReview` disabled that is `hooks.combinedSummary` disabled or `hooks.autoFix` disabled. With `hooks.selfReview` enabled no flag combination suppresses it — the self-review stage ships a `## Open` whenever it renders a final report at all; the one non-flag exception is the zero-change branch, which closes the chain without a report and therefore without the offer. Never invent a placement outside the `## Open` section, and never render it in a non-terminal fix round: it belongs only to the turn that closes the chain.
