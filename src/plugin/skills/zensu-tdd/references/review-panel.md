# Phase 6 step 10.3–4b: panel, merge and required judges

Read this entire reference after [review-packet.md](review-packet.md) and before spawning reviewers. Every reviewer uses the same canonical packet reference from step 10.2c.

## Native task prompt format

Copy the helper's exact `REVIEW-PACKET: ... sha256:...` output onto **its own line** in every task's `prompt`. The line must start with `REVIEW-PACKET:` and end immediately after the digest. Never put prose, a bullet, indentation, quotes or backticks before it, or append any text after the digest. For example, `Exact evidence reference: REVIEW-PACKET: ...` is invalid. The fences below only display prompt contents; do not include fences in the actual prompt. Replace the example packet line with the exact helper output, preserving the same path and digest across this round.

Each task also supplies its unique `name`, `description`, the indicated `agent_type`, and `mode: "sync"`. Packet fields are injected by the hook; do not reconstruct them in these prompts. Use `(no findings)` only when the actual merged list is empty.

Built-in aspect (`agent_type: zensu:review-aspect`; substitute the selected perspective), or a discovered custom persona with its own native `agent_type` and named focus:

```text
perspective: correctness
REVIEW-PACKET: /absolute/project/.zensu/reviews/run.example/round-1-packet.json sha256:<64-hex-digest>
```

Primary judge (`agent_type: zensu:review-judge`):

```text
REVIEW-PACKET: /absolute/project/.zensu/reviews/run.example/round-1-packet.json sha256:<64-hex-digest>
merged_panel_findings:
- (no findings)
```

Independent second judge (`agent_type: zensu:review-judge`): copy the same original primary input and append the separate final line `judge_run: second`. Both judges receive the same panel findings, never each other's results.

```text
REVIEW-PACKET: /absolute/project/.zensu/reviews/run.example/round-1-packet.json sha256:<64-hex-digest>
merged_panel_findings:
- (no findings)
judge_run: second
```

3. **Review fan-out (read-only, parallel).** **Native review engine:** run the configured custom-agent panel directly. Preserve the same evidence packet, panel activation, independent judge runs, verification, one-shot review ticket and convergence; external acceleration does not replace a completed native review. Spawn ONE parallel batch (the review fan-out the main-thread model above sanctions, as it sanctions step 4b's judge pair): one `zensu:review-aspect` agent per perspective of the panel that `ZENSU_ROOT="{plugin_root}" bash -c 'source "$ZENSU_ROOT/hooks/lib/zensu-config.sh"; zensu_review_panel'` prints — `lean` (the default): `correctness`, `design`, `security`; `full`: `conventions`, `bugs`, `architecture`, `tests`, `security` — and when `hooks.aspectActivation` is enabled (the default) pipe THIS packet's `changed_files` (one path per line) into `node "{plugin_root}/hooks/lib/aspect-activation-v1.js" --panel <panel> --round <round>` first, with `<round>` = `re` on a re-review the post-review directive launched and `first` otherwise, and spawn only the perspectives it answers `spawn`. The lean panel skips `security` on a documentation-only change set and re-reviews a fix round with `correctness` alone, by design; the full panel skips at most `architecture` on a change set carrying no production code and `tests`/`security` on a documentation-only one; both fail OPEN on empty or unclassifiable input, so a narrowed panel is always a proven reduction and never a guess. Log every `skip <aspect> <reason>` line as `ASPECT SKIPPED — <aspect> (<reason>)` and carry the count into the final report — a panel that shrank silently is indistinguishable from one that was never spawned. A FAILING command (node missing, non-zero exit) is different: log `ASPECT ACTIVATION UNAVAILABLE — <reason>` and spawn the whole panel — PLUS one agent per step-2b `spawn <name>` persona (task tool, `agent_type=<name>`; its findings MUST carry the persona's uppercased `<NAME>-` ID prefix per the README persona contract). Give every batch member the exact `REVIEW-PACKET` reference and name its perspective (or persona) separately; the hook injects the complete REVIEW PACKET v1. The built-in aspect agents receive enforced `reviewer-readonly-v1`: `view`/`grep`/`glob` only, no bash/build/test, no workflow mutation, and no nested agents. For a bare `zensu-review-<name>` task, the hook also validates the nonsymlinked `.github/agents/zensu-review-<name>.agent.md` definition against its declared name and the canonical change set's activation rules before injecting those identical bytes. The definition belongs to the packet's repository root; a missing, renamed or no-longer-active persona is a blocker to correct, never permission to send a hand-built substitute. This evidence delivery does not grant tool permissions or primary-judge authority. Repo-local custom personas remain neutral `host-profile-v1`; audit and constrain their own `tools:` frontmatter to the same read trio and repeat the no-mutation/no-nesting contract in the spawn prompt. **A repo-custom persona's prompt is repo-authored, so it carries no evidence-discipline block of its own** — unlike every plugin agent, and unlike the confined workers `/zensu-pr-team-review` and `/zensu-plan-review` spawn their custom seats as. view the canonical block at run time from `{plugin_root}/docs/evidence-discipline.md` (the delimited `<!-- zensu:evidence-discipline -->` … `<!-- /zensu:evidence-discipline -->` region, verbatim, never a copy pasted into this skill) and prepend it to every custom persona spawn prompt, ahead of the REVIEW PACKET. If the file is unreadable, log `PERSONA CARRIER UNAVAILABLE — <reason>` and spawn anyway: the `SubagentStart` hook is the other carrier and the panel must not silently shrink. view the severity rubric the same way from `{plugin_root}/docs/review-severity.md` (the `<!-- zensu:review-severity -->` … `<!-- /zensu:review-severity -->` region) and prepend it right after the evidence-discipline block, so a persona rates findings on the same scale as the built-in aspects; the rubric has no second carrier, so when its file is unreadable log `PERSONA CARRIER UNAVAILABLE — review-severity: <reason>` and spawn anyway. If a persona spawn fails because the subagent type is not registered, log `PERSONA SKIPPED — <name> (not registered)` and continue the batch.

4. **Merge in-thread.** Collect every `## Aspect:` findings list plus every custom persona's list, deduplicate (same `file:line` raised by multiple perspectives → keep the highest confidence), and sort CRITICAL → IMPORTANT → SUGGESTION → by file path. Then number the merged findings `R<k>-F<n>` in that order and keep each id in its finding text, where `k` is this review's round: 1 for the first review, and the number the post-review directive names for every later one. This is the synthesis the standalone reviewer used to perform in its own Phase 5; you now do it here.

4b. **Judge second pass (config-gated).** On a re-review with the lean panel, skip this step: the judge reviews the first review only. Otherwise resolve the flag with the real merge semantics: `ZENSU_ROOT="{plugin_root}" bash -c 'source "$ZENSU_ROOT/hooks/lib/zensu-config.sh"; zensu_hook_enabled reviewJudge && echo on || echo off'`. On `on` (the default), spawn ONE `zensu:review-judge` agent (task tool, `agent_type='zensu:review-judge'`) with the same `REVIEW-PACKET` reference plus `merged_panel_findings` outside the packet, and plus `findings_ledger` when the post-review directive's review-convergence clause resolved a `status=ok` ledger for this review; on a first review, first resolve the independent second run at the end of this step, because its spawn shares this tool message. It re-reads the changed files fresh using dedicated read tools only and returns `JUDGE-*` deltas covering the panel's blind spots (cross-cutting, requirement drift, missed edge cases, panel quality). Merge the deltas BEFORE fix routing: a `Panel-FP:`-prefixed meta-verdict neutralizes the finding it references — keep BOTH visible in the merged list, retitle the referenced finding `[Panel-FP-neutralized — do not fix]` and set it to SUGGESTION (a referenced CRITICAL is never dropped outright, only annotated + downgraded), and exempt neutralized items from fix routing in EVERY severity mode, including `autoFixIncludeSuggestions`; every other JUDGE finding joins the list normally and takes the next free `R<k>-F<n>` id after the panel findings, beside its `JUDGE-n` label (a finding that quotes an earlier ledger id still takes its own new id), except a covers line (`[STILL OPEN] <id> covers <panel-id>`, `[NOT FIXED] <id> covers <panel-id>`): it is a meta-verdict like `Panel-FP:`, takes no id, and names the panel finding it covers — a `[STILL OPEN]` line keeps that finding under the earlier ledger id, a `[NOT FIXED]` line leaves it its own id. Flag disabled → skip straight to step 4c. **Independent second run, first review only:** when no post-review directive named a fix round, resolve the flag the same way with `zensu_hook_enabled reviewJudgeSecondRun`; on `on` (the default), the tool message that spawns the judge also spawns a second `zensu:review-judge` with the identical input plus a last line `judge_run: second`. Neither run sees the other's deltas, so the two cross-cutting attempts stay independent and run side by side rather than one after the other. The second run only adds findings, labelled `JUDGE-B<n>`, and you enforce that here: a `Panel-FP:` line, a `[NOT FIXED]` or `[STILL OPEN]` tag or a `## Gaps` section in its report neutralizes, re-ids and gaps nothing; log each as `JUDGE SECOND RUN RULE BREACH — <what>` and merge only its findings, preserving the first run's authority over meta-verdicts. Merge the union after the first run's deltas: a `JUDGE-B<n>` finding naming the same defect at the same `file:line` as a merged finding that is not `[Panel-FP-neutralized — do not fix]` adds its label to that finding and raises its severity when the second run rated it higher; every other one, one that names the defect of a neutralized finding included, takes the next free `R<k>-F<n>` id at its own severity. A second run that fails, answers `REVIEW PACKET INVALID` or returns no parseable report leaves the first run's result standing: log `JUDGE SECOND RUN UNAVAILABLE — <reason>` and carry it into the final report. Flag disabled → the first run stands alone, as before. **Required primary completion:** when this step enables the primary judge, its native completed result must be a parseable `## Aspect: judge` report with findings or `- (no findings)`. `REVIEW PACKET INVALID`, a missing report, spawn failure or tool error is NOT completion, and an additive second judge never substitutes. Preserve the failed result, verify the canonical packet/receipt, and retry the primary ONCE with the SAME reference, original merged findings and a short explanation of the invalid assumption (the canonical summary is the close evidence). If the retry also fails, report `REVIEW INCOMPLETE — primary judge unavailable` and leave the chain open; never issue/consume a review ticket or label the chain successful. Native dispatch enforces completion for this generation, round and packet hash.
