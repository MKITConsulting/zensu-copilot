# Phase 6 steps 6d to 9: acceptance and implementation report

6d. **Live Acceptance Verification** (BOTH strict and vanilla mode, after steps 1 and 5b; an Autopilot-bound chain skips it: its VALIDATE stage verifies every criterion unless the run was started with `--no-validate`, and the bound terminus says which). Invoke `/zensu-verify-feature` with `--chain --log {log_file}` (read `{plugin_root}/skills/zensu-verify-feature/SKILL.md` with native view and execute it in this main thread with the stated input). It lists this chain's active `AC-###` criteria with `COPILOT_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --acceptance-status --log {log_file}`, exercises each one against the RUNNING feature (browser, simulator app, API, CLI, queue, wherever it lives) and records one verdict per criterion with `--acceptance-record`; a check decided by an exit code runs through `--evidence-run --scope acceptance`, so the plugin observes it rather than you. `--chain-done` refuses while any active criterion lacks a `pass` on the tree that ships (§Acceptance Verification Gate in `docs/gates.md`), and every later edit makes the records stale. A `fail` or `partial` criterion routes exactly like a failed suite in step 1: add a fix step whose `Covers` names it, fix it under the still-active gate, re-run steps 1 and 5b, then run 6d again for the criteria that are not `pass`. A criterion this environment cannot drive is `partial` with the reason, never `pass`, and goes to the user.
