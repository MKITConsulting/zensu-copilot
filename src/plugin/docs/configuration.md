# Configuration for Copilot CLI

This reference describes the native Copilot package. It preserves the shared Zensu policy configuration and marks inactive source-host settings explicitly. See [runtime and identity](copilot-runtime.md) and [host parity](parity.md).

Every hook, every config flag, the merge order, and the environment
variables the native host or the Zensu dispatcher supplies. Nothing here is required to run the plugin —
defaults are the supported configuration.

### Native hooks

Copilot registers native events in `com.github.copilot/hooks/hooks.json`. The dispatcher normalizes native tools, arguments, outcomes and child identities before running the shared policy hooks. The native `hooks/registry.json` lists sequenced policy handlers; `com.github.copilot/hooks/hooks.json` registers them with Copilot. See the complete [event map](parity.md#native-hook-map).

Native task selectors include `zensu:code-reviewer`, `zensu:review-aspect`, `zensu:review-judge`, `zensu:plan-review-worker`, `zensu:pr-review-worker` and `zensu:zensu-plm`. The `task` call also requires native `name`, `description`, and `prompt` arguments. Registration files use bare agent names; Copilot adds the plugin namespace.

### Native child capabilities

Built-in reviewers, the PLM analyst, and the two leased review workers may use only
`view`, `grep`, and `glob`. Other neutral children may use the exposed native
`view`, `grep`, `glob`, `edit`, `create`, `apply_patch`, `lsp`, `web_fetch`,
`web_search`, `update_todo`, `task`, `ask_user`, and `skill` tools, subject to
path, identity, and workflow gates. A listed name does not guarantee the host
exposes it. `bash` additionally requires `hooks.subagentShell` and a classified
non-reviewer child identity.

MCP grants require a unique pending native `tool.execution_start` record matching
the exact tool name, arguments, and actor. The event's `mcpConfigServerName`
(or `mcpServerName` when absent) and `mcpToolName` establish provenance; metadata
inside `toolArgs` never does. Exact server `context7` permits only
`resolve-library-id` and `query-docs`. Exact server `zensu` permits operations
prefixed `list_`, `get_`, `search_`, `suggest_`, `view_`, or `validate_`, plus
`analyze_journey_health`, `ghost_get_candidates`, and the journal operations
`pulse_start_session`, `pulse_end_session`, and `pulse_session_summary`. A completed
previous call, ambiguous pending records, or an unknown server/operation grants
nothing. These grants apply to neutral children, not the confined review profiles.

### Hook Opt-Out

The active native handlers are enumerated in `hooks/registry.json`. The configurable subset is listed below; `pre-edit-tdd-reminder.sh` has no on/off flag of its own — it is bypassed for the whole session via the `ZENSU_TDD_GATE` env var in the environment GitHub Copilot CLI starts with and passes through for whole sessions frozen into vanilla mode by `tddImplementation` (see that row below), and `session-start-evidence-discipline.sh`, `pre-write-plugin-data-guard.sh` and the browser consent pair `pre-browser-navigation-consent.sh` / `post-browser-navigation-consent.sh` have none by design (see [Evidence Discipline](architecture.md#evidence-discipline), [Plugin-Data Guard](gates.md#plugin-data-guard) and [Browser Consent Gate](gates.md#browser-consent-gate)). Any flagged hook can be disabled via `~/.zensu/config.json` without forking, editing, or uninstalling the plugin.

**Visible opt-outs (bypass ledger).** Env-var escapes stay free — no gate ever blocks on them — but they are no longer silent: while a TDD session is active (chain-state `active`), each gate records the escape it was bypassed through (`ZENSU_TDD_GATE`, `ZENSU_BASH_WRITE_GATE`, `ZENSU_MCP_GATE`, `ZENSU_SECRET_SCAN`, `ZENSU_CHAIN`, `ZENSU_EDIT_LANDING_GATE`, `ZENSU_REQUIREMENTS_GATE`, `ZENSU_FULL_SUITE_GATE`, `ZENSU_ACCEPTANCE_GATE` — env or inline prefix) into the per-session state file, deduplicated per gate name and carrying gate names only (never command payloads or values; entries are validated at write and read against a closed allowlist of those nine names plus the retired `ZENSU_TEST_WITNESS`, which stays readable so a ledger an older installation wrote still renders, pre-existing junk sanitized and bounded by the closed allowlist + per-name dedup). The ledger records gate escapes ONLY, so every name rendered under "Gates bypassed" is genuinely a gate that was escaped; operator interventions that are not escapes — notably the `/zensu-recover-chain` repair — record their provenance as a workflow `history` entry inside their own transaction instead of borrowing this surface. One recording semantic for every site: the escape is recorded when it short-circuits the gate's **decision point** — the zensu CLI gate records when a `zensu` invocation is actually present; `ZENSU_MCP_GATE` is also honored (and therefore also recorded) by the bash source-write gate at its own any-bash-command decision point while that opt-in gate is on, so it can appear in sessions that never ran the zensu CLI; the full-suite gate records at `--chain-done` only where it applies (a ticket-bound standalone terminus or a bound `pass`, in a git work tree, with the claimed ticket matching); the acceptance gate records at `--chain-done` on a ticket-bound standalone terminus with the claimed ticket matching, and never for a bound Autopilot chain, which it does not check; the secret-scan gate's inline escape records only on write-channel commands while its exported env escape records on the first scanned payload of any kind; `zensu-log.sh append` carries a SECOND `ZENSU_SECRET_SCAN` site with a semantic neither of those covers — it records whatever `ZENSU_SECRET_SCAN=off` reaches its OWN process environment — which includes an inline prefix written in front of the `append` command itself, since a shell assignment before a command is exported into it and the verb sees one environment either way — once per `append` invocation that takes it, and only while `ZENSU_SESSION_KEY` resolves (that verb carries no session bind of its own, so outside a Zensu-started session it records nothing); what it never records is a prefix on some OTHER command, because it does not consult the decider ; inline prefixes are reported by the command parsers themselves (quoted spellings and mixed commands included; heredoc bodies, argument mentions, and channel-less commands excluded), and a command that ends up DENIED never mints a ledger entry from the denying gate — deny wins over markers WITHIN each gate (sibling hooks on the same tool call decide independently, so a gate that individually allowed may still have recorded its own escape even when another gate denied the call; over-reporting, never under-reporting). A config-disabled gate (`hooks.<flag>:false`, or an opt-in flag such as `hooks.bashWriteGate` that is not `true`) has no decision point — deliberate standing configuration is not ledgered. The chain-end summary surfaces the list as `Gates bypassed during this session: …` (`/zensu-autopilot` prints the build-level union into the PR body as `Gates bypassed during build: …`), sourced via `zensu-log.sh --bypass-list`, which is THREE-valued: the list; `none` — permitted only after it read a valid document that recorded no escape; or, on exit 3, an `UNREADABLE — …` line on stdout meaning the document could not be validated, which is explicitly NOT a clean ledger (a further non-zero exit, notably exit 2 for an unavailable session identity, leaves stdout empty and writes to stderr). `--bypass-note <gate>` is the write verb, itself scoped to active sessions. The ledger resets at every `--tdd-begin` and `--tdd-reset`, and BOTH echo any non-empty outgoing ledger as `previous-run bypasses (cleared now): …` so multi-run unions have a durable trace; recording is fail-open — a ledger failure never breaks the gate. **What the ledger does and does not prove.** It detects a DAMAGED document, not an authenticated deletion: `validateWorkflowState` is structural, and the `bypasses` array carries no MAC or monotone counter, so a document edited in place but left schema-valid still reads `valid` and renders `none`. The ledger is a structural audit record, not an authenticated history. **This paragraph is the authoritative residual list; the skill and test surfaces point at it rather than restating it.** The releases that end a session without the chain-end report now render the line themselves, on the agentStop hook's stderr — the operator channel every other release message there already uses: `ZENSU_CHAIN=off`, `hooks.chainEnforcer=false`, and the cap release after a chain fails to converge. The `--chain-done` verb renders it too, on the same channel, so the zero-change terminus discloses through either entry point — a gate escape needs no file change to be recorded. All four are silent only when the ledger is genuinely empty. What remains genuinely undisclosed is the schema-valid edited document above, and a ledger cleared by `--tdd-begin` or `--tdd-reset` — both of which echo the outgoing entries first, so the trace survives in the run log rather than in the report. Read the line as "what a readable document recorded", never as "no gate was escaped".

| `pendingReviewTtlHours` | `stop-chain-enforcer.sh` + `hooks/lib/zensu-doctor-report.js` | **One value, THREE questions, and their safe directions do not agree — read this before picking a number.** Integer freshness window (default `6`, valid range `0..8760`) for the deferred-review `pending-review` marker. Question one: when the next interactive `agentStop` finds a marker whose `ts` is older than this many hours, it is treated as abandoned — cleared instead of adopted — so a stale marker (e.g. from an interrupted deferred-review run that never called `--pending-review-done`) cannot hijack an unrelated later session. A SHORTER window is safer here. Question two: whether a durable Autopilot run holding this working tree blocks a deferred-review `agentStop` (the `stop-chain-enforcer.sh` row above). A marker past the window is abandoned work and no longer sustains that refusal, so a shorter window is RISKIER here — it retires the very evidence that keeps a foreign run from interleaving. `0` is not a neutral middle: it *disables* the hijack guard while being the *strictest possible* setting for the second question, where a marker of any age sustains the refusal indefinitely for as long as the holding run stays nonterminal. Note also that for this refusal the TTL governs the MARKER only: a retained `.claim` file carries no TTL there, so once a claim exists the refusal stands at every setting, `0` included. Question three: the same window is, separately, the LEASE of an adopted claim. The adopting `agentStop` starts it when it hands the review off, and every later `agentStop` of the owning session that blocks for that review renews it; once the owning session has gone more than this many hours without such a `agentStop`, another session's `agentStop` may adopt the review. A recorded owner process id never extends the lease. A shorter window hands an abandoned review to another session sooner, but it also hands over a review whose session merely went that long without a blocking `agentStop`, for example during one very long turn; `0` never expires the lease, so a handed-off review stays with its session until that session finishes or releases it. The "Who holds an adopted review" paragraph under the subagent-safety section in `docs/session-control.md` states the whole ownership rule. With `logging.timestampStyle:none`, the marker intentionally carries no `ts`, so freshness falls back to the regular file's `mtime`; timestamp formatting never disables the TTL guard. A **blank** value is treated as absent and falls back to the default rather than to `0` — `Number('')` is `0`, which passes the range check, so a wrapper fault that exported an empty string would otherwise switch the guard off silently; the sibling `implStopNudgeAfter` row states the same rule and both now read through one bounded-integer reader. The `/zensu-doctor` `autopilot:` row does NOT read this value, and a previous revision of this row said it did: that row reports how long a holding run's owner has been silent against each run verb's OWN window — `autopilotOwnerActivityTtlHours` for `autopilot_adopt_run` and `autopilotReleaseOwnerActivityTtlHours` for `autopilot_release_run` — and each key's behaviour at `0` is documented in its own row below. **Neither run verb reads this value any more.** `--autopilot-release` used to borrow it, so a deployment that tuned it — including to `0` — tuned the release's liveness check as a side effect; that tuning no longer carries over, and the `autopilotReleaseOwnerActivityTtlHours` row states what to set instead. |

| `autopilotOwnerActivityTtlHours` | `hooks/lib/zensu-autopilot-state.sh` (the `adopt` worker mode) + `hooks/lib/zensu-doctor-report.js` | Integer freshness window (default `1`, valid range `0..8760`) deciding when a durable Autopilot run's OWNING session still counts as active for `zensu-log.sh --autopilot-adopt`. Adoption refuses with exit `7` while the owner's workflow document `.zensu/state/tdd-phase-<owner>.json` was modified within this many hours. **It governs adoption ONLY:** `--autopilot-release` reads its own key, `autopilotReleaseOwnerActivityTtlHours` (next row), because the two verbs answer the same liveness question with opposite costs of being wrong — an adoption taken too early is recoverable, a cancel is not — so each window is sized against its own verb. **The window is not the only thing that decides, and sizing the number without knowing that is the mistake this sentence exists to prevent.** The guard STANDS DOWN — at any window value, `8760` included — when there is NO workflow document for the recorded owner, and when the owner's active pointer no longer designates the run, which is abandonment evidence that owes nothing to a clock. Both are files any session in the project can create or delete, and each stand-down writes an `owner liveness unchecked: ...` line to stderr rather than refusing. A BACKDATED document leaves no line at all: it simply reads as stale, so the stderr line is a trace of the stand-downs, never of every way past the guard. A document dated in the FUTURE REFUSES with exit `7` while that pointer still designates the run: its accidental causes — a jumped clock, a skewed container, an NFS mount, an mtime-preserving restore — leave the owner LIVE, and adopting there would unlink that live owner's pointer, while the victim's own adopt-back is refused for as long as the adopter's document stays fresh. **A takeover refreshes the adopting session's OWN workflow document inside the project lease** (`touch -c`, which creates nothing), so a second adoption or a release queued behind it is refused with exit `7` instead of reading the just-adopted run as silent; a document that is not a safe regular file is left alone and the verb says so. **The signal is a file mtime, not a process.** The agentStop hook writes that document at every turn end, so it is a per-turn heartbeat — which means it cannot tell a session that is thinking from one that ended moments ago, and this window is how long the benefit of the doubt lasts. It is deliberately NOT `pendingReviewTtlHours`: that value answers how long a deferred-review marker stays meaningful. A SHORTER window frees a genuinely abandoned run sooner and risks taking a run from an owner that was merely idle; a longer one is the reverse. `0` disables the check with one stderr line disclosing it — never silently. A **blank** value falls back to the default rather than to `0`, the same rule the `pendingReviewTtlHours` and `implStopNudgeAfter` rows state, and every one of these windows reads through one bounded-integer reader. **The verdict is visible before anything moves:** `--autopilot-adopt --run <id>` WITHOUT `--confirm` is a read-only report over the same checks — it prints the liveness verdict against this window, including which stand-down applies, and what `--confirm` would do, writes nothing, and exits with the code a confirmed run would take. **The `/zensu-doctor` `autopilot:` row quotes this window for the adoption half** of a foreign holding run's owner-silence clause; `hooks/lib/zensu-doctor.sh` resolves it through its getter, exports it as `ZDOC_OWNER_ACTIVITY_TTL_HOURS` and re-resolves it from the bound record's project root, and at `0` that half is REPLACED by an explicit switched-off disclosure naming this key — never dropped, because a disabled guard must not render like an armed one. A run whose PENDING stage is `TDD_RUNNING` withholds the adoption half entirely, since `--autopilot-adopt` refuses a live inner chain with exit `3` before it reads any document. Note the bound honestly: `ownerSessionId` is an unauthenticated field in a session-writable directory, so this window is a correctness aid against accidental takeover, not a lock. |
| `autopilotReleaseOwnerActivityTtlHours` | `hooks/lib/zensu-autopilot-state.sh` (the `release` worker mode) + `hooks/lib/zensu-doctor-report.js` | Integer freshness window (default `6`, valid range `0..8760`) — how long `zensu-log.sh --autopilot-release` keeps giving a durable run's OWNING session the benefit of the doubt before it applies an IRREVERSIBLE `CANCEL`, after which every later verb refuses on the terminal stage. The release refuses with exit `7` while the owner's workflow document `.zensu/state/tdd-phase-<owner>.json` was modified within this many hours. While enabled (the default), every session start and every subagent spawn carries the option-quality rule, and every prompt a one-line reminder of it: any option set put to the user must contain the best long-term / end-user solution and rank it first, with cost stated inside an option rather than used to demote or omit it. It is switchable — unlike `session-start-evidence-discipline.sh`, which has no flag by design — because it governs how a decision is presented, not whether a claim is true. Consequence worth knowing before you rely on it: the flag resolves through the normal merge, where the project-local `.zensu/config.json` wins per key, so a repository can carry `bestSolutionFirst:false` and silence the main-thread injection for whoever opens it. It cannot silence the subagents reviewing it: the `subagentStart` leg ignores the flag, because a reviewer is the process whose instructions must not be editable by its subject. Default `true`. |
| `context.compactionNudge` | Not active on Copilot CLI | Inapplicable desktop-pool setting. The source-host occupancy nudge is skipped because native measured utilization is unavailable; transcript length is never converted into a percentage. |
| `context.nudgeThreshold` | Not active on Copilot CLI | Reserved setting with no native nudge effect until measured context utilization is supplied. |
| `context.windowSize` | Not active on Copilot CLI | Inapplicable desktop-pool setting; manually setting a window size does not supply missing native usage measurements. |

**Resolution rules:**

- File missing -> all hooks active (default, backward compatible), except the opt-in keys below
- Key missing -> hook active
- Only an explicit boolean `false` disables a hook
- Opt-in hook keys are the exception: `bashWriteGate` and `tddImplementation` take effect only as an explicit boolean `true`; absent, `false` or a quoted `"true"` leaves them off
- Override the config path via the `ZENSU_CONFIG` environment variable

> Flag names are **case-sensitive** and must be **JSON booleans**, not strings. A misspelled key or a quoted `"false"` is silently treated as enabled, and a quoted `"true"` on an opt-in key is silently treated as off.

**Disable selected workflow automation:**

```json
    "autoTdd": false,
    "chainEnforcer": false,
    "autopilotEnforcer": false,
    "autoFix": false,
    "pulseSession": false
  }
}
```

**Selective opt-out (e.g. silence the pulse banner only):**

```json

    "pulseSession": false
  }
}
```

A reference file with the opt-in flags off is included as [`config.example.json`](../config.example.json) at the repo root. Copy it to `~/.zensu/config.json` if you prefer an explicit baseline.

If `autoFix:false`, the scoped reviewer completion is still claimed exactly once and receives a ticket-bound close/self-review handoff, but no findings are changed and no auto-fix loop runs.

### Config Resolution Order

The plugin **deep-MERGES** the config files field by field to build the effective `config.json` — global as the base, the project-local file overlaid on top. Precedence, lowest to highest:

1. `$HOME/.zensu/config.json` (global base). Every key here applies unless a higher level overrides it.
2. `$COPILOT_PROJECT_DIR/.zensu/config.json` (project-local overlay). Wins **per key** over the global file; keys it does not set **fall through** to the global value. Auto-discovered — `COPILOT_PROJECT_DIR` is set by GitHub Copilot CLI for all hook subprocesses, no user setup required.
3. `$ZENSU_CONFIG` (environment override). When set, it is used **verbatim as a full override — no merge**, the explicit escape hatch for a single shell session.

A missing or malformed file is treated as `{}`, and any key absent from the merged result falls back to the hook's built-in default. So a downstream project can commit a project-local `.zensu/config.json` that sets only a few keys (e.g. enabling `autoFixIncludeSuggestions:true`) and the developer's other global settings still apply.

**Three keys deviate from this section.** `hooks.reviewerSpawnAutoAllow` and `hooks.subagentShell` are exempt from the merge and the per-key overlay, while `ZENSU_CONFIG` still replaces the global file and the project overlay outright. Both follow the `zensu_hook_enabled_strict` rules rather than the merged `cfg()` — the shell reader itself for `reviewerSpawnAutoAllow`, and a port of it inside the capability gate for `subagentShell` — because each governs a capability the plugin grants ITSELF rather than a protection it runs. There is no merge and no per-key overlay: a `false` in ANY candidate withdraws the grant, so a project-local file cannot re-arm one the user withdrew globally; a present-but-malformed candidate withdraws it instead of degrading to `{}`; and an empty candidate list withdraws it rather than falling back to the built-in default. Their rows above state the full rule. `hooks.sessionAutoAdopt` deviates in ONE respect: `false` is sticky across the layers, while an unreadable or malformed layer degrades to enabled as it does for every ordinary key, because enabled runs a repair rather than a bypass; its row above states that rule. No other key should be given either treatment without the same argument.

> If your project commits a `.zensu/config.json` and a developer also has `~/.zensu/config.json`, the two are **merged field by field** — the project-local file wins per key, and keys it omits keep the developer's global value. Use `ZENSU_CONFIG=/path/to/other.json` to bypass the merge entirely for one session.

### Log Timestamp Style

The `/zensu-tdd` workflow writes a session log under `.zensu/logs/YYYY-MM-DD-HHMM_tdd-<slug>.log` with one line per RED/IMPL/GREEN phase. The wall-clock prefix on each line can be reformatted or suppressed via `~/.zensu/config.json`:

| Style | Inline format | Example |
|---|---|---|
| `wall` (default) | `[HH:MM:SS]` | `[14:23:45] step1 RED test_isOdd — FAIL` |
| `relative` | `[+HH:MM:SS]` from session start (< 24h); `[+Dd HH:MM:SS]` for deltas ≥ 24h | `[+00:01:23] step1 RED test_isOdd — FAIL` / `[+1d 03:45:12] step42 GREEN test_persist — PASS` |
| `none` | no prefix | `step1 RED test_isOdd — FAIL` |

Filenames retain the `YYYY-MM-DD-HHMM` session timestamp for uniqueness across multiple sessions on the same day; only the inline log-entry prefixes are affected.

Example (relative timestamps):

```json
{
  "logging": {
    "timestampStyle": "relative"
  }
}
```

Invalid values, missing keys, malformed JSON, or a missing `node` binary all fall back to `wall`.

### Full-Suite Evidence

`zensu-log.sh --evidence-run` runs a test command itself and records the real exit code. A `full` or `scoped` run is also bound to a fingerprint of the project's working tree, taken together with the nested work tree it ran in when there is one, so a later edit makes the record stale. Records live in the plugin's private data directory (`$COPILOT_PLUGIN_DATA/evidence-run/v1/`): the file tools of the reviewer and of a neutral subagent cannot read them, the subagent shell guard denies them by name, and edit/create cannot reach them. A bash redirect from the main thread, or an obfuscated subagent command, can still write them.

```bash
COPILOT_PLUGIN_DATA="<plugin data>" bash "<plugin root>/hooks/lib/zensu-log.sh" --evidence-run --scope full
```

| Argument | Effect |
|---|---|
| `--scope full\|lint\|build\|coverage\|scoped\|acceptance` | Required. `full`, `scoped` and `acceptance` fingerprint the working tree at start and end. A local chain's full-suite verdict reads only `full` runs; a chain whose full suite runs in CI reads its `scoped` runs too ([Full Suite in CI](#full-suite-in-ci)). An `acceptance` run is the observed evidence one acceptance record cites ([Acceptance Verification](#acceptance-verification)). |
| `--cmd '<shell>'` | The command to run. It runs from a private script file under `set -o pipefail` in `bash --noprofile --norc`, with stdin connected to the null device. It runs in the caller's working directory when that directory lies in the git work tree of the bound project root (for a root outside git: inside the root), and otherwise in the project root with a notice on stderr, because the tree fingerprint describes the project root. The plugin's own bindings (`ZENSU_SESSION_KEY`, `COPILOT_PLUGIN_DATA`, `COPILOT_PLUGIN_ROOT` and the rest of the Session Control exports) are removed from its environment, and `COPILOT_PROJECT_DIR` is the caller's own value. |
| `--show tail\|all` | `tail` (default) prints the last 80 lines once the run ends; `all` prints the whole output. The full output always stays in a private log file whose path is printed first, so a background run can be inspected while it runs. |
| `--if-stale` | With `--scope full`, skips the run when the newest `full` record is green on the current tree. With `--scope scoped`, skips it when the newest run of the same command is green on the current tree. |
| `--local` | Runs `--scope full` in a chain whose full suite runs in CI. Without it, such a run is refused with exit `2`, writes no record, and the refusal says it is not a suite failure. Pass it only when the user asked for a local full run. |
| `--log <run log>` | Appends one machine-authored `EVIDENCE RUN — scope=… exit=… duration=… tree=… record=… \| cmd: …` line to a TDD run log through the normal `append` path (secret scan and path redaction included). `--start <epoch>` feeds the `relative` timestamp style. |

The exit status is the command's own. A signal maps to `128 + n`, and a signal to the runner stops the whole process group and records the run as `interrupted`. A usage error, a refused command or an unavailable store exits `2`. The last output line is one summary: `zensu evidence-run: scope=… exit=… duration=…s tree=… record=… cmd=…`, with the command passed through the secret scan.

The tree fingerprint uses a temporary index, so the real index is never touched. `.zensu/` is excluded, so the run's own artifacts never make it stale. A `full` or `scoped` run whose command starts with a literal `cd <dir>` into a git work tree nested inside the project's own work tree, such as a worktree under `.zensu/worktrees/`, is fingerprinted over the project and that work tree together (see [Full-Suite Gate](gates.md#full-suite-gate)). A cwd in such a work tree runs the command in the project root instead, as `--cmd` describes, and an `acceptance` run keeps the project's fingerprint. Over 20000 untracked files or 512 MiB of untracked content, or when `git` fails, the record carries no tree and names the reason. Retention keeps the newest 40 records per session and scope, so acceptance runs never evict a full-suite record, sweeps sessions idle for 14 days, and caps each output log at 5 MiB by cutting its middle.

| Key | Default | Effect |
|---|---|---|
| `evidence.fullSuiteCommand` | unset | The command `--scope full` runs when no `--cmd` is given. While it is set, an explicit `--cmd` that differs from it is refused, so every `full` record names the configured suite. Unset, `--scope full` needs `--cmd`. |
| `evidence.fullSuiteGate` | `required` | How `--chain-done` applies the full-suite verdict ([Full-Suite Gate](gates.md#full-suite-gate)): `required` refuses a missing, red, running, interrupted or stale record; `advisory` prints the same verdict marked `(advisory, not blocking)` and closes the chain. Any other value is treated as `required`, and the verdict says so. |
| `evidence.fullSuiteRunner` | unset | `ci` or `local`: the team-wide choice of where a chain's full suite runs, the last rank of the [Full Suite in CI](#full-suite-in-ci) ladder. `local` always wins. `ci` takes effect only while the CI pull-request pipeline is verified. Any other value is ignored. |
| `evidence.ci.workflow` | unset | The workflow file under `.github/workflows/` that runs the full suite on pull requests, for example `ci.yml`. Unset, the plugin picks the first workflow that triggers on `pull_request` and passes verification. |
| `evidence.ci.job` | unset | The job name pattern that runs the suite. `*` matches any text, so `test (*)` binds every matrix shard. Unset, the plugin proposes the job that looks most like a test run. |

```json
{
  "evidence": {
    "fullSuiteCommand": "npm test",
    "fullSuiteGate": "required"
  }
}
```

#### Full Suite in CI

A chain can leave its full suite to the repository's CI pull-request pipeline, so no full run happens on this machine. The tests affected by the change still run locally through `--scope scoped`, and the terminus closes as `FULL SUITE — deferred-ci` when every local test run on the current tree is green. The full suite then runs when a pull request is opened or updated. A red pull-request pipeline is possible, and the choice accepts it.

```bash
COPILOT_PLUGIN_DATA="<plugin data>" bash "<plugin root>/hooks/lib/zensu-log.sh" --full-suite-policy --refresh
```

The verb prints `full suite: ci`, `full suite: ask` or `full suite: local`, followed by the CI job, the command it runs, the local full-suite command, the age of the last pull-request run, whether the check blocks merges, the conditions found in the workflow, and who decided. `/zensu-tdd` runs it in Phase 0. On `ask`, an interactive chain asks the user once; a delegated or headless chain treats `ask` as `local`. `/zensu-full-suite` records the answer and reports the state with `--status`.

**Verified** means all of this holds for a GitHub.com repository: a workflow under `.github/workflows/` triggers on `pull_request` (`pull_request_target` never counts), the repository is not a fork, and a job matching the bound pattern concluded `success` or `failure` in a completed pull-request run of the last 30 days. `skipped` and `cancelled` jobs do not count. Whether the check blocks merges is read from branch protection and rulesets and shown, never required. Path filters, branch filters and the `if:` conditions of the bound job are shown, not evaluated. The verification uses `gh api` and is cached in `$COPILOT_PLUGIN_DATA/ci-contract/v1/`. `--refresh` reuses a proof younger than 24 hours and otherwise verifies again over the network. When that fails for a transient reason, such as no network or a missing or failing `gh`, the cached proof keeps counting for up to 7 days and the policy line names the failure. A refresh that finds the pipeline no longer qualifies removes the cached proof. Every other read uses the cache alone: a proof older than 24 hours is marked `(stale)`, and one older than 7 days no longer counts. An edit to the workflow file voids the proof at once. Other forges resolve to `local`.

**Precedence.** `local` in any rank wins at once. CI runs need a `ci` choice in some rank and a verified pipeline:

1. the session marker `.zensu/state/full-suite-<session>.json` (`/zensu-full-suite --ci|--local|--auto --session`);
2. the record for this clone in the plugin data directory, shared by every worktree of the clone (`/zensu-full-suite --ci|--local|--auto --repo`);
3. `evidence.fullSuiteRunner` in the config.

With nothing recorded and a verified pipeline, the state is `ask`. A process inside CI (`CI`, `GITHUB_ACTIONS`, `GITLAB_CI`, `TF_BUILD` or `BUILDKITE`) never defers the suite to itself. `--tdd-begin` records the chain's runner in a snapshot, and the terminus honours CI only when the chain began with it: a switch to CI takes effect with the next chain, while a switch to local applies at once. Without a verified pipeline the chain runs the full suite locally, exactly as before, and the policy line names the reason. When a chain that chose CI closes locally, the terminus prints `FULL SUITE — local runner | <reason> | decided by: <rank>`.

**Not covered.** A full-suite command the model runs by hand is not blocked; only the runner refusal and the skill text steer it. The chain does not wait for CI, and nothing makes the branch reach a pull request. Autopilot gates still run their own test gate locally. The per-clone record and the snapshot live in the plugin's private data directory, which a bash redirect from the main thread, or an obfuscated subagent command, can still write.

### Acceptance Verification

Every active `AC-###` criterion of a standalone chain's plan is verified live before the chain
closes ([Acceptance Verification Gate](gates.md#acceptance-verification-gate)). `/zensu-tdd`
Phase 6 step 6d and `/zensu-self-review` drive it through `/zensu-verify-feature --chain`, which
records one verdict per criterion:

```bash
COPILOT_PLUGIN_DATA="<plugin data>" bash "<plugin root>/hooks/lib/zensu-log.sh" --acceptance-status --log <run log>
COPILOT_PLUGIN_DATA="<plugin data>" bash "<plugin root>/hooks/lib/zensu-log.sh" --acceptance-record --ac AC-001 --verdict pass --driver browser --log <run log> <<'EVIDENCE'
Opened the settings page, saved the value, reloaded and saw it again.
EVIDENCE
```

| Argument | Effect |
|---|---|
| `--ac <AC-###>` | The criterion. It must be an active `AC-###` row of the plan this session's edit-landing receipt names; an unknown, `FR-###` or deprecated id is refused. |
| `--verdict pass\|fail\|partial` | `partial` means the criterion could not be proven here, and it blocks like `fail`. |
| `--driver <name>` | One of the nine driver ids of `/zensu-verify-feature`. `api`, `cli`, `async`, `iac`, `custom` and `library` are observed: they need `--evidence-run` unless the verdict is `partial`. `browser`, `mobile` and `desktop` are attested. The spellings of earlier releases stay accepted, so a running session whose skill text still names them can record: `desktop-native` is attested and `artifact` is observed. A `desktop` record is stored as `desktop-native`, the spelling every earlier installation still reads, because after an update both installations can read the same session's records. |
| `--evidence-run <er1 id>` | An `--evidence-run --scope acceptance` record of this session. It must have completed on the current tree without changing it, and its exit code must agree with the verdict. |
| `--log <run log>` | Required for both verbs. Its stem must equal the run log this session's edit-landing receipt records. `--acceptance-record` appends one `ACCEPTANCE — …` line to it. |
| stdin | The evidence text, at most 2000 characters, in English whatever language the conversation is in, because up to 200 characters of it land in the run log. It is refused when empty or when it matches a secret pattern, and paths are redacted before it is stored. |

`--acceptance-status` prints one `ACCEPTANCE STATUS — …` line plus one line per criterion and
exits 0 only when every active criterion passes on the current tree. The summary line ends with
the remedy segments a `--chain-done` refusal would print (`run:`, `fix:`, `add:`, `restore:`);
act on the segment, never on the exit code alone, because verifying an unchanged tree again
cannot turn a failing criterion. Records live in
`$COPILOT_PLUGIN_DATA/acceptance-verify/v1/records/`; retention keeps the newest 20 records per
criterion and 400 per session, and sweeps sessions idle for 14 days.

| Key | Default | Effect |
|---|---|---|
| `evidence.acceptanceGate` | `required` | How `--chain-done` applies the acceptance verdict: `required` refuses while an active criterion lacks a `pass` on the current tree; `advisory` prints the same verdict marked `(advisory, not blocking)` and closes the chain. Any other value is treated as `required`, and the verdict says so. |

| `COPILOT_PLUGIN_DATA` | — | Set by the dispatcher from the host plugin-data value or the documented Copilot fallback. Helpers validate their private record under this directory. This is not a credential. |
| `COPILOT_SESSION_ID` | — | Set by the dispatcher from the correlated native root session. Stateful helpers require a matching private record, installation, runtime digest and project binding; the ID is not a secret or capability. |
| `COPILOT_PROJECT_DIR` | — | The dispatcher-bound project cwd. The immutable Session Control record remains the workflow-state anchor after a verified reanchor; a later shell directory alone cannot choose another workflow. |

The `COPILOT_*` helper values above are supplied by the native hook on allowed `bash` calls. No `COPILOT_AGENT_TYPE`, generic session placeholder or environment-propagation file is assumed. Child authority comes from native hook identity, not a model-supplied environment variable. No foreign-host identity aliases are defined. `ZENSU_BOUND_SESSION_ID` independently protects the bound native session selector.

| `PLUGIN_DATA` | Host-provided when available | Native host plugin-data root accepted by the native hook when `COPILOT_PLUGIN_DATA` is not already bound. |
