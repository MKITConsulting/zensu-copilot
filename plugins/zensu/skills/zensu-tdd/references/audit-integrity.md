# Phase 6 steps 4 to 6c: implementation integrity audits

4. view plan and implementation files. Verify every step's description matches the actual code. For `[W]` steps, verify wired code is actually USED (not dead imports). If gaps → fix through another TDD cycle → re-verify.
5. **mtime Discipline Audit**. For every Feature step marked `[G]`:
   - Resolve the IMPL file list from the `{step_id} IMPL completed — files: {list}` log entry — parse it exactly as step 5b a) does: the `files:` list only, never the commentary after ` | `, or `stat` is handed prose as a path.
   - Resolve the test file from the step's `{step_id} RED {test_name}` log entry.
   - Capture mtimes: `test_mtime=$(stat -f %m {test_file})` (Linux: `stat -c %Y {test_file}`); `impl_min_mtime=$(stat -f %m {impl_files} | sort -n | head -1)`.
   - If `test_mtime > impl_min_mtime`: the step was Test-After. Mark the plan step `[!]` and append `DISCIPLINE VIOLATION: test-after detected ({test_file} mtime > {impl_file} mtime)` to the log.
   - Aggregate: if > 20% of Feature steps carry `[!]`, the final log line MUST read `TDD DISCIPLINE VIOLATED — {N}/{M} steps test-after, audit FAIL` and Phase 6 is NOT complete. Surface this prominently in the final user-facing report so the developer notices.
5b. **Edit Landing Audit** (runs in BOTH strict and vanilla mode). Verify that every edit you CLAIMED actually landed — a mechanical or bulk replacement that matched nothing produces NO diff, so the file never enters `changed_files` (step 10.2), the whole review chain is blind to it, and the suite stays green because it was green anyway.
   a) Run it: `bash "{plugin_root}/hooks/lib/zensu-edit-landing.sh" --log {log_file} --project "{project_root}" --baseline "$BASELINE_SHA" --session-epoch "$SESSION_EPOCH" --session "{session_id}"` — on a review-fix round add `--dirty-before {file}` listing the paths already dirty when that round began. The library extracts the `IMPL completed — files:` / `WIRED — files:` claims, normalizes them to repo-root-relative paths, enumerates the project-anchored change set (unborn HEAD, mid-run commit and non-git cases included), and writes the receipt that `--tdd-complete` requires. Exit 0 = every claim landed or is provably exempt; 1 = at least one is not; 2 = the audit could not judge the claims or could not write its receipt, and the lines it printed say which. Do NOT re-implement the recipe in prose here — the library IS the recipe, and `tests/structure/test-edit-landing-audit.sh` is what holds it honest.
   **Session binding:** Always pass `--session "${COPILOT_SESSION_ID}"`. In an active native workflow, omission exits 2 before grading and prints `AUDIT SESSION REQUIRED` plus the exact recovery command. Follow that command, retain the original dirty scope, and supply current `--predicates` where needed. `STANDALONE AUDIT` cannot complete a workflow; `--inventory` only inspects claims.
   b) The final line `EDIT LANDING AUDIT — claims=<n> landed=<n> not_landed=<n> unverified=<n> pending=<n> exempt_ignored=<n> exempt_verified=<n>` IS the terminal summary; there is no separate close marker. The canonical review-packet helper derives that same line from the clean JSON receipt. React to the verdict. Copy every line that is not `EDIT LANDED` verbatim into the run log, mark Phase 6 NOT complete, and carry it into the final report AND the CHAIN-END SUMMARY. `EDIT NOT LANDED` — the claim has no corresponding change. `UNVERIFIED (foreign root)` — the claim resolves into ANOTHER repository, which this run can neither grade nor write a receipt for; `/zensu-tdd` is single-root, so run the chain in the repository the claims name or land the work in the anchor, and never re-point `--project` at the foreign root to make the line disappear (the receipt would land where the terminus never reads it). `UNVERIFIED (no work tree)` — the claim resolves outside the audited root and NO git work tree was found above it either, so there is no repository to name and nothing to grade it against; that is a different remedy from the foreign-root one — re-check the path the claim names rather than looking for another repository to run the chain in. `PENDING PREDICATE` — the file was already dirty before this round, so membership in the change set proves nothing about THIS round; re-read the target predicate yourself (is the NEW string present? is the OLD occurrence count 0?). `UNVERIFIED (undetermined root)` — the ancestor walk from the claim gave up before it reached a work tree or the top of the filesystem, so nothing here establishes which repository the claim belongs to; treat it as unplaced, not as unlanded, and shorten the path or re-check the claim. `UNVERIFIED` — nothing gradeable was logged. `EDIT LANDING AUDIT FAULT` — git refused or failed on the audited root (a `safe.directory` "dubious ownership" refusal, a HEAD lookup git aborted, a listing git could not produce), and the line names the git command, its exit status and git's own message. NO claim was graded and the audit exits 2. Once scope is bound, a nonclean checkpoint preserves the cumulative context and any previous claim certifications; a Git fault retains that scope with `auditFailure` instead of deleting it. Neither implementation completion nor the terminus accepts this failed audit as clean. It is not a verdict about any claim: land, withdraw or re-claim nothing for it. Resolve the git error, then re-run the audit; a `safe.directory` exception changes the user's global git configuration, so adding one is the user's decision, not yours. **Bound on the foreign-root verdicts, because it decides which of these you will actually see**: `zensu-log.sh append` REDACTS the run log, so a claim under `$HOME` — a sibling repository beside this one — is rewritten to `~/...` before it lands and is no longer an absolute path to the grader. Such a claim reaches `EDIT NOT LANDED`, not `UNVERIFIED (foreign root)`, and the remedy above for that line — land it in the anchor — is the WRONG one for work that belongs in another repository. When a claim you spelled under `$HOME` comes back `EDIT NOT LANDED`, re-read the claim before landing anything. A claim spelled absolutely INSIDE the anchor is redacted to `<project>/...` and is handled: the grader strips that placeholder. **A green test run is never the evidence for any of these**: it corroborates the command, not the change.
   c) **Resolve pending predicates with checked evidence.** Re-read each target and the exact claim labels in the append-only log. For an already-dirty file, prove the intended change using `--predicates <JSON file>`; a prose assertion or a passing suite does not clear `PENDING PREDICATE`. The helper matches each entry's exact `step` label (including spaces) and normalized project-relative `path`, verifies the current file's SHA-256, and checks literal presence/absence without evaluating code, shell or regular expressions. At least one nonempty `present` or `absent` literal is required (up to 100 of each, each at most 4096 bytes). For deletion of a whole file, use only `{"step":"SR1","path":"src/obsolete.js","missing":true}`; absence of a file is different from absence of a string in an existing file. A deletion proof requires a file previously observed by this cumulative audit or an actual Git changed path that is now absent; it cannot clear a never-created unlanded claim merely because the file is missing.

      Example: after reading the intended edit, generate the proof file from the actual bytes, replacing the example path, labels and literals with the real claim-specific predicates. Never paste a guessed hash. An updated previously certified file needs proof for **every historical and new claim label on that file**; repeat the checked predicate set for each relevant label. An unchanged previously certified claim retains its certification.

      ```bash
      PREDICATE_FILE="$(mktemp /tmp/zensu-predicates.XXXXXX)"
      node - "$PROJECT_ROOT" "$PREDICATE_FILE" <<'NODE'
      const fs = require('node:fs');
      const path = require('node:path');
      const crypto = require('node:crypto');
      const [root, output] = process.argv.slice(2);
      const file = 'src/cli.js';
      const sha256 = crypto.createHash('sha256').update(fs.readFileSync(path.join(root, file))).digest('hex');
      const claims = ['S1', 'SR1'].map(step => ({
        step, path: file, sha256,
        present: ['const MAX_INPUT_BYTES = 1024 * 1024;'],
        absent: ['const MAX_INPUT_BYTES = Infinity;']
      }));
      fs.writeFileSync(output, JSON.stringify({schema: 'edit-landing-predicates-v1', claims}));
      NODE
      ```

      Re-run the **same audit over the same run log and bound root**, adding `--predicates "$PREDICATE_FILE"` and retaining captured baseline, session epoch and round dirty-before inputs. Before predicate, file or Git grading, the helper checkpoints `auditScope` in a nonclean receipt, so an interrupted or failed attempt cannot erase newly bound context. An active generation cannot use `--receipt -`; omit that option for the canonical receipt-producing audit, or use `--inventory` for read-only claim inspection. Omitted context inherits the persisted scope; an empty or different baseline/epoch cannot weaken it, and omitting `--dirty-before` cannot clear its cumulative dirty paths. In a cold handoff, omit an unavailable argument only to inherit already persisted context; never substitute an empty invented value. If original required context was never persisted and cannot be recovered, report the blocker. The helper alone writes receipts and state; never edit, delete or replace them to remove a pending claim. Require an actual exit-0 clean receipt before implementation completion or successful chain closure. The terminus also checks that the receipt still describes this generation, log and current tree; later edits require another audit with current predicates.

   d) Do NOT auto-fix — same severity as the Precondition Drift Audit below. **An unlanded claim clears only by LANDING the claimed edit at the path the claim names and re-running the audit; an already-landed pending claim additionally needs the checked predicate proof above.** Withdrawing a claim is still a recorded state change — log `CLAIM WITHDRAWN — {step_id}: {file}`, mark that plan step `[!]`, and leave both the finding and the Phase-6-NOT-complete state standing — but it does NOT clear the verdict and never did: the run log is append-only and the grader retires no claim, so `--tdd-complete` keeps refusing a receipt recording `clean: false` however the withdrawal is worded. **Withdrawal is not an exit; it is a record.** If the claimed edit genuinely cannot be landed in this generation, do NOT claim success or call a passing `--chain-done`; preserve the failed chain and obtain authorization to abandon that generation and ARM A NEW ONE with the corrected scope — `--tdd-begin` retires the previous generation's receipt — UNLESS it prints `RECEIPT RETIREMENT UNRESOLVED`, which means the new generation is not ready; resolve the named filesystem condition through the helper's documented recovery and retry. Never remove a receipt to conceal this generation's unresolved claims, edit the run log, or weaken audit context hoping for a different verdict over the same claims. The two exemptions the library grants — a gitignored-by-design artifact it proves with `git check-ignore`, and a step logged `WIRED (verified, no change)` — must already hold when the audit runs; writing either one afterwards to clear a finding IS the violation.
6. **Precondition Drift Audit**. Detect silent substitution.
   a) view the `## Preconditions` table from the plan. Collect the names of every CLI/tool listed (column 1 of rows where Type=CLI).
   b) For each such CLI name `X` where the Decision was `install` or substitute=`{name}`: search the log file for any invocation of `X` (or the named substitute) in IMPL/WIRED entries using fixed-string word matching: `grep -F -w "$X" {log_file} || grep -F -w "$substitute" {log_file}`. If a CLI name contains regex metacharacters (`.+*?[]()|\`), DO NOT use `grep -E` with interpolation — always prefer `grep -F -w` for CLI-name searches.
   c) **Drift conditions**:
      - Decision was `install` but `X` never appears in an IMPL/WIRED log entry → DRIFT (silent skip).
      - Decision was `skip` but `X` appears in an IMPL/WIRED log entry → DRIFT (silent inclusion against user decision).
      - Decision was substitute=`Y` but neither `X` nor `Y` appears → DRIFT (neither contracted tool ran).
   d) If any drift: append `PRECONDITION DRIFT — {tool}: decision={d}, actual={observed}` to the log, mark Phase 6 NOT complete, and surface prominently in the final report. Do NOT auto-fix — drift is a discipline violation, same severity as mtime discipline failure (existing step 5).
6b. **Cross-Layer Value Flow Audit** (Principle 2 — Cross-Layer Value Flow Pairing).
   a) view the plan's `## Cross-Layer Value Flow Pairings` table. For every row:
      - Verify the Characterization Step `{step_id_B}` is marked `[G]` AND has its three RED + IMPL + GREEN log entries (same contract as the per-step logging contract in Principle 3).
      - Verify mtime: the Characterization test file mtime PRECEDES the IMPL file mtimes of the originating Feature step `{step_id_A}` (same comparison as step 5). If `char_test_mtime > origin_impl_mtime`: append `CROSS-LAYER PAIRING TEST-AFTER — {step_id_B} characterization mtime > {step_id_A} impl mtime` and mark Phase 6 NOT complete.
      - Verify the characterization asserts at the unchanged layer's OWN seam (DB row / response body / persisted file / returned struct), NOT at a caller-side mock. view the test file; if its top-level assertions only inspect mocks created in the same test, append `CROSS-LAYER PAIRING MOCK-ONLY — {step_id_B} asserts only on caller mock, not on unchanged layer's seam` and mark Phase 6 NOT complete.
   b) **Missing-pairing detection.** Re-scan IMPL log entries for Feature/Bug-Fix steps. For each step, inspect the diff of its IMPL files for added literals matching field-name / payload-key patterns (`'foo':`, `"foo":`, `foo=`, `&foo=`) that did not exist in the pre-step version of those files. For each such added literal, grep the IMPL files of OTHER steps in this plan for the same literal — if no other step in this plan added the same literal AND the plan's Cross-Layer Pairings table has no row pairing this step to a layer that consumes the literal, append `CROSS-LAYER PAIRING MISSING — {step_id} added literal "{literal}" with no paired characterization` and mark Phase 6 NOT complete.
   c) Do NOT auto-fix — pairing violations are a discipline violation, same severity as mtime and precondition drift.
6c. **Requirements Coverage Cross-Check** (warning level). view the plan's `## Requirements` table. Verify (a) every Steps-table row has a non-empty `Covers` cell naming at least one requirement ID from the table, and (b) every requirement ID **not marked deprecated** is named by at least one step's `Covers` cell (deprecated rows are exempt by design — the never-recycle rule keeps them). On a miss append `REQUIREMENT COVERAGE WARNING — {step without Covers | requirement ID without covering step}` to the log and surface it in the final report. Warning level only — it does NOT mark Phase 6 incomplete. If the plan has no `## Requirements` table (legacy plan), skip silently.
