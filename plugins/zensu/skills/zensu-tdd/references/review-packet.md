# Phase 6 step 10.1–2c: implementation close and canonical packet

Read this entire reference before closing implementation or creating the round's review packet. Follow the ordering in [review-chain.md](review-chain.md).

1. Mark implementation complete. **This verb REFUSES on two preconditions: the step 5b edit-landing receipt RECORDING A CLEAN AUDIT, and a usable `## Requirements` table in this session's plan** — run the audit first and fill the table, or completion fails closed, naming the command in both cases. A receipt is not a token: only `clean: true` under a known schema is accepted, so an audit that reported `EDIT NOT LANDED` must be ANSWERED by landing the claimed edit at its recorded path and re-running the audit, never merely re-running it to regenerate the file. A withdrawal records the failure but NEVER clears it; when it cannot be landed, preserve the failed generation and use the explicitly authorized fresh-generation recovery in step 5b c). The receipt requirement is armed by a changed tree OR by a logged claim, so a chain whose work landed somewhere the anchor cannot see is gated exactly like a dirty one. Pass `--plan {plan_file}` — the cwd-independent spelling defined in Principle 3 — so the table is judged against the plan you actually wrote; without the flag the gate derives it from the receipt's run log, which is the same stem. The flag is bounded: it must name a plan inside `{project_root}/.zensu/plans/` whose stem matches the run log this session's edit-landing receipt records, so it cannot silently pick up an unrelated plan. The bound is as strong as that receipt, not stronger — the receipt is an ordinary file in the project tree, so this is anchoring, not enforcement. For a standalone chain run `COPILOT_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --tdd-complete --plan {plan_file}`. For a delegated Autopilot chain run the exact bound form `COPILOT_PLUGIN_DATA="{plugin_data}" bash "{plugin_root}/hooks/lib/zensu-log.sh" --tdd-complete --plan {plan_file} --autopilot-run "$RUN_ID" --autopilot-attempt "$ATTEMPT" --chain-id "$CHAIN_ID"`, using the immutable values accepted by this generation's bound begin. This arms the Stop-hook backstop (`stop-chain-enforcer.sh`): you cannot end your turn until the chain terminates or its Stop cap is hit. A non-zero bound completion that is NOT a precondition refusal is stale or mismatched: stop without spawning a reviewer or changing the current generation. **Classify by SHAPE, never by a closed pair of literals** — the refusals grew and a literal list goes stale silently: a receipt that records `clean: false`, one that carries no verdict, one that is unreadable or unparseable, and one that describes a DIFFERENT run log all name the receipt without carrying the words `no edit-landing receipt`. Every refusal whose text names the edit-landing receipt or the plan's `## Requirements` table is a precondition refusal, meant to be fixed and retried; only a refusal naming neither is stale or mismatched.

2. **Canonical change set.** Run `node "{plugin_root}/hooks/lib/review-packet-v1.js" changes --root "{project_root}" --baseline "$BASELINE_SHA"` (omit `--baseline` only for an unborn repository with no captured SHA). Its JSON `root` is `$TOP`; `changed_files` is the complete repository-relative union of tracked worktree/index changes, untracked non-ignored files, and the captured-baseline-to-HEAD range, excluding workflow internals. It supports nested project directories and literal filenames; invalid baselines and Git failures refuse instead of returning an empty list. Use this same helper in review and self-review; there is no separate Phase 6 step 5b enumeration recipe. Read each relevant literal-path diff anchored at `$TOP`; include the baseline range for mid-run commits, and native `view` for new untracked files. Do not manually reduce the canonical Git list. Outside a Git repository the helper explicitly returns `kind: explicit-no-git` and `changed_files: null`: take the exact known edited/deleted paths from this session's implementation claims, inspect them, and put that explicit list in the packet input. The helper snapshots only those paths and reports the limitation; never claim a complete repository diff or Git tree proof for this mode. An actual Git error is still a refusal, never a fallback to non-Git mode.

2b. **Persona discovery (repo-local).** Pipe the step-2 list into `node "{plugin_root}/hooks/lib/persona-activation.js" "$TOP/.github/agents"` — it decides which `.github/agents/zensu-review-*.agent.md` personas join (activation globs vs changed paths; no `activation:` field = always joins; cap 5, matched-before-always-join, each lexicographic). Empty output = no custom personas; a FAILING command (node missing, non-zero exit) is different — log `PERSONA DISCOVERY UNAVAILABLE — <reason>` and continue without customs. Append every `skip`/`drop` verdict to the run log humanized: `PERSONA SKIPPED — <name> (no activation match | malformed)` / `PERSONA DROPPED — <name> (over cap)` — no silent omission.

2c. **Create one immutable `REVIEW PACKET v1`.** Create one unique directory for this generation with `mkdir -p "{project_root}/.zensu/reviews"` followed by `REVIEW_DIR="$(mktemp -d "{project_root}/.zensu/reviews/run.XXXXXX")"`; retain it for this generation. Use native file creation to write `$REVIEW_DIR/round-<k>-input.json` with six nonempty string fields (and, only outside Git, an explicit `changed_files` string array of this session's known changed paths): `implementation_summary`, `requirements_baseline` (stable requirement IDs or `none`), `diff_summary`, `test_evidence` (verbatim evidence-run, CHECKPOINT and ACCEPTANCE STATUS lines), `build_evidence`, and `coverage_evidence`. An audit not run must say `not run — <reason>`; never fabricate a success. Run `node "{plugin_root}/hooks/lib/review-packet-v1.js" create --root "{project_root}" --baseline "$BASELINE_SHA" --input "{input_json}" --session "{session_id}" --out "$REVIEW_DIR/round-<k>-packet.json"` (the helper derives the receipt path from the canonical session key; omit an absent unborn baseline). The helper derives `changed_files` and the current Git tree fingerprint, validates the clean receipt and produces the exact canonical `EDIT LANDING AUDIT — claims=... landed=... not_landed=... unverified=... pending=... exempt_ignored=... exempt_verified=...` summary. No additional close marker exists. It writes once and prints `REVIEW-PACKET: <absolute path> sha256:<hash>`. Copy that exact output onto its own line in every native reviewer, persona, judge and consume prompt in this round: no prose prefix, indentation, bullet, quotes, backticks or appended text. `REVIEW-PACKET:` starts the line and the digest ends it. See the minimal task prompt examples in [review-panel.md](review-panel.md) and [review-completion.md](review-completion.md). Reuse the same line for every call; do NOT copy, reword or rebuild the packet into individual prompts. The native pre-tool hook checks the reference against the current tree and this session's current receipt, then injects the same immutable packet bytes. After any edit or audit replacement, create a fresh packet and repeat the required review stages; an old primary result never covers the changed evidence. Reviewers consume the injected block and MUST NOT open the main-only `.zensu/reviews` file. Put perspective/persona, `review_scope`, judge findings and ledger OUTSIDE the packet. A failed packet build is a blocker to repair, not permission to dispatch a hand-written substitute. A non-workflow standalone review may still use an explicit legacy inline packet with `not run — <reason>` evidence.
